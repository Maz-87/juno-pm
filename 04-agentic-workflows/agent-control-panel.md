## What Juno Is Doing

Synthesize insights from feature requests into key themes/problem statements and output into a Notion table

## Four Levers

**Stop Conditions** (Loop):

Juno should stop attempting to retrive the data after x2 failed attempts. Attempts should be staggered 1 hour apart. After x2 failed attempts Juno should not attempt to retrive the data again until the next time the job is scheduled to run.

**Structured Tool Outputs** (Tools):

If Juno successfully retrives the latest data from JIRA and Slack it should update the Notion table.

If Juno fails to retrive the latest date from either JIRA or Slack it should trigger an alert to the '#product-management' Slack channel. This alert message should specify the source that cannot be accessed (eg. JIRA) and the error code returned by the API. If multiple sources are unavailable these should be sent as separate messages.

**Confidence Thresholds** (Verification):

High confidence: the JIRA ticket or Slack message is added to the Notion dashboard where its problem statement is clearly evident and unambiguous.
Mediium confidence: the JIRA ticket or Slack message has an ambiguous problem statement and should be added to the Notion dashboard with a note for the PM to review
Low confidence: the JIRA ticket or Slack message does not contain a problem statement and should be compiled into a separate Notion table for the PM to manually follow up with the requester.

**North Star** (Context):

Each request from JIRA and Slack must have a clear problem statement free from ambiguity in order to be included
Each insight/problem statement group should have a corresponding Slack or JIRA ticket request reference

## Rules of Engagement

**Agency Permission:**

Juno can read JIRA (but it cannot write).
Juno can read Slack and only write to '#product-management' channel
Juno can read and write to the Notion dashboard/table

**Access Control:**

JIRA, Slack, Notion

**Fallback Protocols:**

Low-context request: if a ticket is too vague to assign to a theme, Juno puts it in an “Unclassified” group with a one-line reason, rather than guessing.
Low-confidence theme: if Juno isn’t confident a cluster reflects a single problem, it labels the theme “Needs PM review” and shows which tickets caused the doubt.
Missing or broken source: if Jira, Slack or Notion is unreachable, or a ticket link can’t be verified, Juno stops, reports which source failed, and does not publish a partial table as if it were complete.
Possible private data: if a request contains customer personal data, Juno excludes it from the summary and flags it for the PMs.
Rubric failure: if a spot check finds a hallucinated theme or ticket link, Juno’s output is paused and reverted to the last approved version until a PM reviews it.
Rollback functionality: PMs can manually revert back to a previous version of the Notion dashboard if the updates published by Juno are not desired.

**Checkpoints:**

Weekly review: PMs spot-check a sample of themes (approx 5) against the source tickets using the rubric before the output is treated as final.
